# RAG 구축 과정

문서를 검색해 LLM 답변의 근거로 넣는 RAG(Retrieval-Augmented Generation) 시스템을 만들 때 보통 거치는 순서다.

1~5단계는 색인 쪽(오프라인), 6~7단계는 질문이 들어올 때 도는 쪽(온라인)이다. 답이 틀리면 대개 생성보다 앞 단계, 특히 파싱·청킹·검색에서 원인이 나온다. 그래서 평가를 마지막이 아니라 처음부터 같이 만든다.

## 1단계. 문서 수집 { #step-1-collect }

**목적**: 답의 근거가 될 문서를 모으고, 문서마다 출처와 버전을 붙인다.

**하는 일**

- 문서 종류(PDF, HTML, 표가 많은 문서, 이미지)별로 목록을 만든다
- 문서 ID, 제목, 출처, 수정일 같은 메타데이터를 정한다
- 갱신 주기와 변경 감지 방법(해시, 수정일)을 정한다

**흔한 선택지**: 파일 저장소 동기화(문서가 한곳에 모일 때), 스크래핑(웹 공개 문서), 스케줄 배치(주기 갱신이 필요할 때)

**흔한 실수**

- 메타데이터 없이 본문만 모아 답변에 출처를 달 수 없다
- 같은 문서의 옛 버전과 새 버전이 함께 색인된다

**관련 기술 노트**: [Airflow](../stack/orchestration/airflow.md)

**관련 내 프로젝트**

- 지식기반 검색 RAG 파이프라인 <!-- PROJECT-LINK: [지식기반 검색 RAG 파이프라인](../projects/agilesoda-finance-rag.md) -->
- 해외 법령 적재 · DB 관리 <!-- PROJECT-LINK: [해외 법령 적재 · DB 관리](../projects/douzone-foreign-law.md) -->

## 2단계. 파싱 (PDF · HTML · 표) { #step-2-parse }

**목적**: 문서를 글자 덩어리가 아니라 제목·문단·표·그림 같은 구조 블록으로 꺼낸다.

**하는 일**

- PDF는 텍스트 레이어를 좌표와 함께 읽고, 스캔본·그림은 OCR이나 VLM으로 읽은 뒤 원본과 대조한다
- HTML은 태그 구조로 제목·문단·표를 구분하고 불필요한 메뉴·광고를 걷어낸다
- 표는 병합 셀과 다단 머리글을 풀어 행·열 의미를 보존한다

**흔한 선택지**

| 선택지 | 언제 고르나 |
|--------|-------------|
| 텍스트 추출 라이브러리 | 텍스트 레이어가 있는 PDF, 깔끔한 HTML |
| 좌표 기반 파싱 | 표 테두리가 없거나 글자가 칸 밖으로 흩어진 문서 |
| VLM | 스캔본, 그림, 도표 설명이 필요할 때 |

**흔한 실수**

- 표를 한 줄 텍스트로 뭉개 행·열 의미를 잃는다
- VLM이 그림에 없는 내용을 지어낸 것을 검수 없이 색인한다

**관련 기술 노트**: [PDF · HTML · 표 처리](../stack/docs/pdf-html-tables.md), [VLM](../stack/llm/vlm.md)

**관련 내 프로젝트**: 지식기반 검색 RAG 파이프라인 <!-- PROJECT-LINK: [지식기반 검색 RAG 파이프라인](../projects/agilesoda-finance-rag.md) -->

## 3단계. 청킹 { #step-3-chunk }

**목적**: 검색 한 번에 질문에 맞는 부분만 돌아오도록, 의미 단위를 깨지 않는 크기로 나눈다.

**하는 일**

- 문단·제목 경계를 따라 나누고, 크기를 넘으면 문장 단위로 다시 나눈다
- 표는 행 단위로 나누고 머리글을 반복해 붙인다
- 청크마다 문서 제목, 소제목 경로 같은 메타데이터를 붙인다

**흔한 선택지**

| 선택지 | 언제 고르나 |
|--------|-------------|
| 고정 길이 + overlap | 구조 정보가 없는 평문 |
| 구조 기반(제목·문단·표) | 파싱 결과에 구조가 남아 있을 때. 대부분 이쪽이 낫다 |
| Parent-child | 검색은 정밀하게, 답변에는 넓은 맥락을 주고 싶을 때 |

**흔한 실수**

- 글자 수로만 잘라 표 행이나 문장이 경계에서 끊긴다
- 청크 크기가 임베딩 모델 입력 한도를 넘는지 검사하지 않는다

**관련 기술 노트**: [청킹](../stack/llm/chunking.md)

**관련 내 프로젝트**: 지식기반 검색 RAG 파이프라인 <!-- PROJECT-LINK: [지식기반 검색 RAG 파이프라인](../projects/agilesoda-finance-rag.md) -->

## 4단계. 임베딩 { #step-4-embed }

**목적**: 청크를 벡터로 바꿔, 단어가 달라도 뜻이 비슷한 질문과 이어지게 한다.

**하는 일**

- 언어(한국어 포함 여부)와 입력 길이를 기준으로 모델을 고른다
- 본문 외에 요약·예상질문 같은 보조 텍스트도 임베딩할지 정한다
- 차원 수와 저장 용량을 계산하고 필요하면 양자화를 검토한다

**흔한 선택지**: 오픈 다국어 모델, 예: bge-m3(한국어 문서를 자체 서버에서 처리할 때), 상용 임베딩 API(운영 부담을 줄이고 싶고 외부 전송이 허용될 때)

**흔한 실수**

- 색인과 질의에 서로 다른 모델이나 전처리를 쓴다
- 모델을 바꾸고 기존 벡터를 다시 만들지 않는다

**관련 기술 노트**: [임베딩](../stack/llm/embeddings.md)

**관련 내 프로젝트**: 지식기반 검색 RAG 파이프라인 <!-- PROJECT-LINK: [지식기반 검색 RAG 파이프라인](../projects/agilesoda-finance-rag.md) -->

## 5단계. 인덱스 설계 { #step-5-index }

**목적**: 키워드 검색, 벡터 검색, 필터가 함께 되도록 저장 구조를 정한다.

**하는 일**

- 텍스트 필드(형태소 분석기 포함), 벡터 필드, 필터용 keyword 필드를 매핑한다
- 문서 종류가 여럿이면 공통 필드와 종류별 필드를 나눈다
- 벡터 인덱스 방식(HNSW 등)과 양자화 옵션을 정한다

**흔한 선택지**

| 선택지 | 언제 고르나 |
|--------|-------------|
| Elasticsearch | BM25와 벡터를 한 곳에서, 필터·집계까지 필요할 때 |
| 전용 벡터 DB·벡터 저장소 | 벡터 검색만 필요하고 규모가 클 때 |

**흔한 실수**

- 한국어 텍스트를 기본 분석기로 색인해 키워드 검색이 약해진다
- 매핑을 나중에 바꾸려다 전체 재색인이 필요해진다

**관련 기술 노트**: [Elasticsearch](../stack/storage/elasticsearch.md)

**관련 내 프로젝트**

- 지식기반 검색 RAG 파이프라인 <!-- PROJECT-LINK: [지식기반 검색 RAG 파이프라인](../projects/agilesoda-finance-rag.md) -->
- 올리브영 클론 프로젝트 <!-- PROJECT-LINK: [올리브영 클론 프로젝트](../projects/personal-oliveyoung-clone.md) -->

## 6단계. 검색 (하이브리드) { #step-6-retrieve }

**목적**: 질문에 맞는 청크를 상위 몇 개 안에 올린다.

**하는 일**

- BM25(키워드)와 벡터(의미) 검색을 각각 돌리고 점수를 합친다
- 메타데이터 필터(문서 종류, 날짜)로 후보를 좁힌다
- 필요하면 상위 후보를 reranker로 다시 정렬한다

**흔한 선택지**

| 선택지 | 언제 고르나 |
|--------|-------------|
| BM25만 | 고유명사·코드·숫자 질문이 대부분일 때 |
| 벡터만 | 바꿔 말한 질문이 많고 용어가 다양할 때 |
| 하이브리드(RRF 등) | 둘 다 섞여 있을 때. 보통 기본값 |

**흔한 실수**

- 평가 없이 가중치를 감으로 정한다
- top-k를 너무 작게 잡아 정답 청크가 잘린다

**관련 기술 노트**: [하이브리드 검색](../stack/llm/hybrid-search.md), [Elasticsearch](../stack/storage/elasticsearch.md)

**관련 내 프로젝트**: 지식기반 검색 RAG 파이프라인 <!-- PROJECT-LINK: [지식기반 검색 RAG 파이프라인](../projects/agilesoda-finance-rag.md) -->

## 7단계. 생성 (프롬프트) { #step-7-generate }

**목적**: 검색된 근거 안에서만 답하게 하고, 근거가 없으면 모른다고 말하게 한다.

**하는 일**

- 시스템 프롬프트에 역할, 근거 사용 규칙, 답 형식을 적는다
- 청크마다 출처를 붙여 넣고 답변에 인용하게 한다
- 컨텍스트 길이와 비용을 보고 넣을 청크 수를 정한다

**흔한 선택지**: 상용 LLM API(품질 우선), 자체 호스팅 모델(외부 전송 불가 환경), 구조화 출력(JSON 스키마로 답 형식을 고정할 때)

**흔한 실수**

- 근거가 없을 때의 행동을 정하지 않아 그럴듯한 답을 지어낸다
- 표 청크의 숫자를 문장으로 옮기며 기간(당기·전기)을 뒤바꾼다

**관련 기술 노트**: [LLM API](../stack/llm/llm-apis.md)

**관련 내 프로젝트**: 해외 법령 적재 · DB 관리 <!-- PROJECT-LINK: [해외 법령 적재 · DB 관리](../projects/douzone-foreign-law.md) -->

## 8단계. 평가 { #step-8-evaluate }

**목적**: 검색과 답변을 따로 숫자로 재서, 바꾼 설정이 실제로 나아졌는지 판단한다.

**하는 일**

- 질문·정답 근거·정답을 담은 평가셋을 만든다
- 검색은 Hit@k, MRR로, 답변은 정답 일치나 심판 LLM 판정으로 잰다
- 설정(청킹, 검색 방식)을 바꿀 때마다 같은 평가셋으로 비교한다

**흔한 선택지**: 사람이 만든 소규모 평가셋(처음 시작할 때), LLM이 만든 질문 + 사람 검수(규모를 키울 때), 심판 LLM 자동 채점(답변 평가를 반복할 때)

**흔한 실수**

- 검색 실패와 생성 실패를 구분하지 않고 최종 답만 본다
- 평가셋이 너무 쉬워 모든 설정이 비슷한 점수가 나온다

**관련 기술 노트**: [RAG 평가](../stack/llm/rag-evaluation.md)

**관련 내 프로젝트**: 지식기반 검색 RAG 파이프라인 <!-- PROJECT-LINK: [지식기반 검색 RAG 파이프라인](../projects/agilesoda-finance-rag.md) -->

## 9단계. 운영 (캐시 · 재처리) { #step-9-operate }

**목적**: 문서가 바뀌어도 색인이 따라가고, 같은 비용 큰 작업을 반복하지 않게 한다.

**하는 일**

- 문서 변경을 감지해 바뀐 문서만 다시 파싱·임베딩한다
- LLM·임베딩 호출 결과와 중간 산출물을 저장해, 재실행 때 실패 지점부터 이어 간다

**흔한 선택지**: Airflow 배치(주기 재색인), Kubernetes 작업 Pod(문서가 많아 병렬 처리가 필요할 때), 인덱스 alias 교체(무중단 전체 재색인)

**흔한 실수**

- 외부 API 일시 오류 한 번에 수천 건짜리 배치 전체가 처음부터 다시 돈다
- 삭제된 문서의 청크가 색인에 남는다

**관련 기술 노트**: [Airflow](../stack/orchestration/airflow.md), [Kubernetes](../stack/infra/kubernetes.md)

**관련 내 프로젝트**: 지식기반 검색 RAG 파이프라인 <!-- PROJECT-LINK: [지식기반 검색 RAG 파이프라인](../projects/agilesoda-finance-rag.md) -->

## 체크리스트 { #checklist }

- [ ] 문서마다 ID, 출처, 버전 메타데이터가 붙어 있다
- [ ] PDF와 HTML에서 표의 행·열 의미가 보존되는지 원본과 대조했다
- [ ] 청크 크기 상한과 overlap을 정한 근거를 말할 수 있고, 크기 초과 청크가 0건인지 검사한다
- [ ] 색인과 질의에 같은 임베딩 모델을 쓴다
- [ ] 인덱스 매핑에서 텍스트, 벡터, 필터 필드를 구분했다
- [ ] BM25, 벡터, 하이브리드를 같은 평가셋으로 비교한 결과가 있다
- [ ] 근거가 없을 때 모델이 어떻게 답해야 하는지 프롬프트에 적었다
- [ ] 검색 지표(Hit@k)와 답변 지표를 따로 잰다
- [ ] 바뀐 문서만 다시 처리하고, 긴 배치가 실패해도 처음부터 다시 돌지 않는다
