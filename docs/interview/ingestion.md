# 수집 예상질문

웹 스크래핑 질문입니다. 개념 정리는 [웹 스크래핑 노트](../stack/ingestion/scraping.md)에 있습니다.

## 웹 스크래핑 {#scraping}

### 정적 페이지와 동적 페이지는 어떻게 구분하고, 도구는 어떻게 고르나요? {#static-vs-dynamic}

??? answer "답 보기"
    서버가 보낸 HTML 원본에 데이터가 이미 들어 있으면 정적, 브라우저에서 JavaScript가 실행된 뒤 채워지면 동적입니다. 페이지 소스 보기에서 데이터가 보이는지로 먼저 확인합니다.

    정적이면 소량은 Requests + BeautifulSoup, 대량 정기 수집은 Scrapy를 씁니다. 동적이면 브라우저 개발자 도구에서 데이터를 가져오는 내부 API를 먼저 찾고, 없을 때만 Playwright나 Selenium으로 브라우저를 띄웁니다. 브라우저 자동화는 느리고 메모리를 많이 써서 대량 수집에는 맞지 않기 때문입니다.

    꼬리: Selenium과 Playwright는 어떻게 다른가요?

### Scrapy를 쓰는 이유는 무엇인가요? {#why-scrapy}

??? answer "답 보기"
    대량 크롤링에 필요한 기능이 프레임워크에 다 들어 있기 때문입니다. 비동기 요청, 중복 URL 필터, 재시도, 요청 간격, 로그, 추출 결과를 정제·저장하는 Pipeline까지 설정으로 씁니다.

    개인 프로젝트 Scrapy 기반 데이터 수집 Pipeline에서는 요청 간격과 재시도를 설정해 과도한 요청을 막고, 로그로 장애와 중간 결과를 확인했으며, Pipeline에서 타입을 정규화해 MongoDB에 적재했습니다. 단점은 JavaScript 렌더링을 못 한다는 것이라 동적 페이지는 내부 API를 찾거나 브라우저 도구와 연동해야 합니다.

### 수집 중 429나 403으로 막힙니다. 어떻게 하나요? {#blocked-429-403}

??? answer "답 보기"
    먼저 요청 속도를 낮춥니다. 429는 너무 빠르다는 신호이므로 요청 간격과 동시 요청 수를 줄이고, 지수 백오프로 재시도합니다. 기본 User-Agent 그대로면 차단되는 경우가 많아 헤더도 확인합니다.

    403이나 404 같은 4xx를 무한 재시도하면 차단이 더 심해지므로 재시도 대상은 타임아웃, 5xx, 429 같은 일시 오류로 한정합니다. 그리고 robots.txt와 이용약관에서 수집이 허용되는지 다시 확인합니다.

    꼬리: 재시도 횟수와 간격은 어떻게 정하나요?

### 사이트 구조가 바뀌어 수집이 조용히 비어 있었습니다. 어떻게 미리 알 수 있나요? {#selector-breakage}

??? answer "답 보기"
    selector가 실패해도 오류 대신 `None`을 돌려주기 때문에, 오류가 아니라 결과를 감시해야 합니다. 필수 필드가 비면 경고를 남기고, 실행마다 수집 건수와 필드별 빈 값 비율을 기록해 평소보다 크게 떨어지면 알림을 보냅니다.

    수집 시각과 원본 URL을 함께 저장해 두면 언제부터 비었는지, 어느 페이지에서 깨졌는지 추적할 수 있습니다.

    꼬리: 알림은 어디로 보내나요?

### 같은 대상을 매일 다시 수집할 때 중복은 어떻게 막나요? {#recrawl-dedupe}

??? answer "답 보기"
    소스 쪽 식별자(원본 URL, 상품 id)를 자연 키로 잡고 upsert로 적재합니다. 그러면 다시 수집해도 같은 행을 갱신합니다. MongoDB면 unique 인덱스 + `upsert=True`, PostgreSQL이면 `ON CONFLICT`입니다.

    증분 수집이라면 마지막 수집 시점 이후만 가져오되, 늦게 반영되는 데이터를 위해 앞 구간을 조금 겹쳐 읽습니다. 더존비즈온의 데이터 수집 API · ETL 파이프라인에서는 초기 데이터 약 50,000건을 수집·적재한 뒤 Airflow DAG로 일 단위 증분 수집·적재를 자동화했습니다.

### 스크래핑 모듈을 API로 제공한 이유와 구조는요? {#scraping-as-api}

??? answer "답 보기"
    여러 곳에서 같은 수집 로직을 다시 짜지 않고 재사용하기 위해서입니다. 더존비즈온의 데이터 수집 API · ETL 파이프라인에서 Selenium·BeautifulSoup 스크래핑 모듈을 API로 제공했고, 수집 요청 처리는 RabbitMQ 비동기 요청과 Redis 캐싱으로 구조화했습니다.

    이 조합의 일반적인 흐름은 API가 Redis에서 같은 요청의 결과를 먼저 찾고, 없으면 작업을 RabbitMQ에 넣고 접수만 응답한 뒤, worker가 수집해 결과를 TTL과 함께 Redis에 저장하는 식입니다. 수집은 오래 걸리므로 API 응답 시간과 분리한 것이 핵심입니다. 큐와 캐시 세부는 [RabbitMQ](processing-streaming.md#rabbitmq), [Redis](processing-streaming.md#redis) 질문에 있습니다.

    꼬리: 같은 URL 요청이 동시에 두 번 들어오면 어떻게 되나요?

### 스크래핑할 때 법적·윤리적으로 무엇을 지키나요? {#scraping-ethics}

??? answer "답 보기"
    이용약관과 robots.txt를 먼저 확인하고, 대상 서버에 부담을 주지 않게 요청 간격과 동시 요청 수를 제한합니다. 개인정보가 포함된 페이지는 수집 대상에서 뺍니다.

    공식 API가 있으면 API를 우선 씁니다. 수집 목적과 범위를 정해 두고 필요한 필드만 저장합니다.
