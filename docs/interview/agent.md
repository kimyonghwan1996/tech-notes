# 에이전트 예상질문

LangGraph와 LLM 에이전트 설계 질문입니다. 개념은 [LangChain · LangGraph 노트](../stack/llm/langchain-langgraph.md), 구축 순서는 [LLM 에이전트 구축 과정](../learn/agent.md)에 있습니다.

## LangGraph · 에이전트 {#langgraph-agent}

### 에이전트와 고정 파이프라인은 어떻게 다르고, 언제 무엇을 쓰나요? {#agent-vs-pipeline}

??? answer "답 보기"
    고정 파이프라인은 처리 순서가 코드로 정해져 있고, 에이전트는 LLM이 상황을 보고 다음 행동(어떤 도구를 쓸지, 끝낼지)을 고릅니다. 요청마다 필요한 도구와 순서가 달라질 때만 에이전트가 필요합니다.

    처음에는 고정 파이프라인으로 시작하고, 정말 분기가 필요한 곳에만 LLM 판단을 넣는 편이 디버깅이 쉽고 비용도 예측됩니다. 예를 들어 개인 프로젝트 AI 기반 숏폼 영상 생성 시스템은 분석 → 스크립트 → 이미지·영상 → TTS → 자막 → 합성 순서가 늘 같아서 고정 파이프라인이 맞는 경우입니다.

    꼬리: 큰 흐름은 고정하고 일부만 LLM이 고르는 혼합형은 어떤 모양인가요?

### LangChain 체인과 LangGraph는 어떻게 다른가요? {#chain-vs-graph}

??? answer "답 보기"
    체인은 프롬프트 → 모델 → 파서처럼 한 방향으로 한 번 흐르고, LangGraph는 state를 들고 노드 사이를 돌며 반복·분기·중단 후 재개를 표현합니다.

    예를 들어 도구 호출 에이전트는 plan 노드에서 모델이 도구 호출을 요청하면 tool 노드가 실행하고, 결과를 state에 붙여 다시 plan으로 돌아가며, 도구 호출이 없으면 끝납니다. 이런 루프와 조건 분기(conditional edge)가 있으면 LangGraph, 직선 흐름이면 체인이 맞습니다. LangGraph는 노드 단위로 흐름이 드러나 추적도 쉽습니다.

    꼬리: checkpointer는 무엇을 해 주나요?

### LangGraph의 state와 reducer는 무엇인가요? 흔한 실수는요? {#langgraph-state-reducer}

??? answer "답 보기"
    state는 그래프 전체가 공유하는 dict 형태의 데이터이고, 각 노드는 state를 읽고 바꿀 부분만 돌려줍니다. reducer는 노드가 돌려준 값을 기존 값과 어떻게 합칠지 정하는 함수입니다. 메시지 목록에는 `add_messages`를 달아 덧붙이게 합니다.

    흔한 실수는 리스트 필드에 reducer를 안 달아서 노드가 돌려준 값이 기존 목록을 덮어쓰는 것입니다. 또 모든 정보를 대화 메시지 하나에 넣으면 상태 추적이 어려워서, 원래 질문, 중간 결과, 오류, 재시도 횟수처럼 필드를 나눠 타입으로 고정합니다.

### 에이전트가 같은 도구를 계속 호출하며 끝나지 않습니다. 어떻게 막나요? {#agent-infinite-loop}

??? answer "답 보기"
    최대 단계 수(recursion limit)와 도구별 타임아웃을 둡니다. 이것이 없으면 루프가 끝나지 않고 비용이 폭주합니다. 반복 엣지마다 종료 조건, 예를 들어 재시도 횟수 상한을 state에 두고 넘으면 실패로 빠지게 합니다.

    원인 쪽도 봅니다. 도구 결과가 모델이 판단하기 어려운 형태이거나, 도구 설명이 모호하거나, 같은 프롬프트로 재시도해 같은 오류를 반복하는 경우가 많습니다. 재시도할 때는 직전 오류 내용을 프롬프트에 넣습니다.

    꼬리: 단계 수 상한에 걸리면 사용자에게 무엇을 돌려주나요?

### 도구는 어떻게 설계하나요? {#agent-tool-design}

??? answer "답 보기"
    도구마다 이름, 설명, 입력 스키마, 출력 형식을 분명히 정하고, 하나의 도구는 한 가지 일만 하게 합니다. 설명이 모호하면 LLM이 비슷한 도구 중 엉뚱한 것을 고르고, 도구 하나가 너무 많은 일을 하면 실패 원인을 나눌 수 없습니다.

    권한은 최소로 둡니다. SQL 도구라면 읽기 전용 계정과 SELECT 검사를 겁니다. 개인 프로젝트 Smart Factory Data Agent에서 질문을 SELECT 전용 SQL로만 변환한 것이 이 원칙입니다. 그리고 도구 결과가 수만 행이면 그대로 LLM에 넣지 않고 요약해서 넘겨야 컨텍스트가 터지지 않습니다.

### human-in-the-loop는 언제, 어떻게 넣나요? {#human-in-the-loop}

??? answer "답 보기"
    되돌리기 어려운 행동 직전에 넣습니다. 메일 발송, 데이터 변경, 결제처럼 실수의 비용이 큰 단계입니다.

    LangGraph에서는 checkpointer가 단계마다 state를 저장하므로, 특정 노드 앞에서 멈추고(interrupt) 사람이 승인하거나 수정한 뒤 같은 지점부터 이어서 실행할 수 있습니다. 같은 `thread_id`로 다시 호출하면 이전 state를 불러와 대화도 이어집니다.

### 에이전트가 잘 동작하는지는 어떻게 평가하고 디버깅하나요? {#agent-evaluation}

??? answer "답 보기"
    요청마다 노드 경로, 도구 호출 인자, 결과, 토큰 수, 지연을 구조화 로그로 남기고, 대표 요청으로 평가셋을 만들어 정답 여부와 도구 선택 정확도를 잽니다. 최종 답만 저장하면 어느 단계에서 틀렸는지 모릅니다.

    실패 사례는 유형별로 모아 도구 설명이나 프롬프트 개선에 씁니다. 프롬프트를 고칠 때마다 몇 개 예시만 눈으로 보지 않고 평가셋을 다시 돌립니다. 이 방식은 RAG 평가와 같아서, 지식기반 검색 RAG 파이프라인에서 검색 → 답변 → 이중 판정 자동 평가로 탐침 질문 96건을 채점한 경험을 그대로 적용할 수 있습니다.

    꼬리: 도구 선택 정확도는 어떻게 정의하나요?

### LangGraph로 에이전트를 만들어 본 경험이 있나요? {#langgraph-experience}

??? answer "답 보기"
    실습 수준입니다. 개인 실습 저장소에서 langchain, langchain-openai, langgraph를 의존성으로 두고 LLM·에이전트 호출을 실습했습니다. 실무에서는 LangChain 체인으로 추출·번역 같은 고정 흐름을 만들었고, 에이전트에 가까운 것은 개인 프로젝트 Smart Factory Data Agent의 질문 → SQL 생성 → 조회 → KPI 분석 → 시각화 흐름입니다.

    그래서 LangGraph는 state, 조건 분기, checkpointer 개념과 루프 종료 조건 같은 운영상 주의점을 중심으로 설명할 수 있고, 실서비스 규모 운영 경험은 없다고 말합니다.

    !!! note "채울 것"
        실습에서 만든 그래프가 무엇을 했는지(노드 구성, 사용한 도구) 한두 문장으로 적어 둡니다.
