# LLM · RAG 예상질문

LangChain, 임베딩, 청킹, 하이브리드 검색, RAG 평가, NL2SQL, VLM, LLM API 질문입니다. 개념 정리는 [기술 스택](../stack/index.md)의 LLM · RAG 노트에 있습니다.

## LangChain {#langchain}

### LangChain은 무엇을 해 주나요? SDK를 직접 호출하는 것과 비교하면요? {#langchain-vs-sdk}

??? answer "답 보기"
    프롬프트, 모델, 출력 파서, 검색기를 같은 인터페이스(Runnable)로 묶어 체인으로 잇게 해 주는 라이브러리입니다. 제공자별 모델이 같은 인터페이스라 모델 교체가 쉽고, `batch`, `stream`, 재시도, fallback을 체인 전체에 붙일 수 있습니다.

    대신 추상화 층이 두꺼워 에러가 났을 때 실제로 어떤 요청이 나갔는지 보기 어렵고, 버전이 빠르게 바뀌어 예전 예제가 그대로 안 돌아가는 경우가 많습니다. 단순 호출 하나면 SDK 직접 호출이 더 짧고 투명합니다. 그래서 추출·번역·요약처럼 고정된 파이프라인에는 LangChain, 세밀한 제어나 최신 기능이 필요하면 SDK를 씁니다.

    꼬리: LCEL은 무엇인가요?

### LangChain을 실제로 어디에 썼나요? {#langchain-usage}

??? answer "답 보기"
    두 곳입니다. 더존비즈온의 데이터 수집 API · ETL 파이프라인에서 LangChain·OpenAI로 초기 데이터와 파일에서 통합 데이터를 추출했고, 매핑·정제·분류 단계를 추가해 데이터 정합성과 LLM 추출 정확도를 개선했습니다.

    해외 법령 적재 · DB 관리 프로젝트에서는 LangChain으로 법령 자동 번역과 참조 법령 탐색을 구현했고, 국가별 법령문 약 20,000건과 번역본을 서비스 DB에 반영했습니다. 두 경우 모두 입력 → 프롬프트 → 모델 → 결과의 고정 흐름이라 체인 구조가 맞았습니다.

    !!! note "채울 것"
        추출 정확도를 어떻게 확인했는지(샘플 검수, 규칙 검증 등) 실제 방법을 한 문장으로 적어 둡니다.

### LLM 출력을 JSON으로 받아야 할 때 어떻게 하나요? {#structured-output}

??? answer "답 보기"
    문자열 파싱에 의존하지 않고 스키마 기반 출력을 씁니다. LangChain이면 Pydantic 모델을 주고 `with_structured_output`을 쓰고, SDK면 JSON Schema 기반 structured output이나 도구 인자 스키마를 씁니다. 문자열 파싱은 형식이 조금만 달라도 깨집니다.

    그래도 출력은 검증합니다. 필수 필드, 허용 값, 타입을 코드로 확인하고, `max_tokens`에서 잘리지 않았는지(stop reason)도 봅니다. 잘린 JSON은 파싱이 실패합니다.

### 같은 입력인데 추출 결과가 매번 달라집니다. 어떻게 하나요? {#llm-output-stability}

??? answer "답 보기"
    추출·분류 작업은 temperature를 0으로 두고, 프롬프트·모델·파서 버전을 고정합니다. 모델 이름에 날짜가 붙은 고정 버전을 쓰면 제공자 쪽 업데이트로 결과가 바뀌는 것도 막을 수 있습니다.

    그리고 평가셋을 두어 프롬프트나 모델을 바꿀 때마다 회귀가 없는지 숫자로 확인합니다. 몇 개 예시만 눈으로 보고 바꾸면 다른 입력에서 깨진 것을 놓칩니다.

### LangChain 버전을 올렸더니 코드가 깨졌습니다. 어떻게 대응하나요? {#langchain-version}

??? answer "답 보기"
    의존성 버전을 고정하고, 올릴 때는 변경 이력과 deprecation 안내를 확인한 뒤 테스트를 돌립니다. `LLMChain`이나 구형 agent executor 같은 예전 API는 LCEL 체인이나 LangGraph로 바뀌었습니다.

    핵심 로직이 라이브러리 내부 클래스에 깊게 묶이지 않게, 프롬프트와 출력 스키마는 내 코드에 두고 모델 호출 부분만 감싸 두면 교체 범위가 작아집니다.

## 임베딩 {#embeddings}

### 임베딩이 무엇이고, 검색에서 어떤 역할을 하나요? {#embedding-basics}

??? answer "답 보기"
    텍스트를 의미가 비슷하면 가까운 위치에 오는 실수 벡터로 바꾼 것입니다. 질문과 문서를 같은 모델로 벡터화하고, cosine 유사도나 내적이 가까운 문서를 찾습니다.

    그래서 표현이 달라도 뜻이 같으면 찾고, 동의어 사전을 따로 관리할 필요가 줄어듭니다. 대신 정확한 숫자, 코드, 고유명사 일치에는 약해서 실제로는 키워드 검색과 함께 씁니다.

    꼬리: dense, sparse, multi-vector는 어떻게 다른가요?

### 임베딩 모델은 어떤 기준으로 고르나요? {#embedding-model-choice}

??? answer "답 보기"
    내 문서와 질문으로 만든 평가셋 성능이 1순위입니다. 공개 벤치마크는 참고만 합니다. 그다음 한국어·다국어 성능, 최대 입력 토큰이 청크 크기보다 큰지, 차원이 메모리 예산 안에 드는지, 로컬 실행인지 API인지(외부 전송, 호출 비용)를 봅니다.

    지식기반 검색 RAG 파이프라인에서는 bge-m3를 썼습니다. 다국어를 지원하고 최대 8192 토큰 입력, 1024차원 dense 출력에 sparse·multi-vector 출력도 함께 냅니다.

    꼬리: 모델을 바꾸면 무엇을 다시 해야 하나요?

### 벡터 인덱스 메모리를 줄이려면요? 정확도는 어떻게 지키나요? {#embedding-quantization}

??? answer "답 보기"
    양자화를 씁니다. float32 벡터를 int8이나 1비트 같은 작은 형식으로 압축하고, 정확도 손실은 원본 벡터로 상위 후보를 재채점(rescoring)해 메웁니다.

    중요한 것은 손실 여부를 같은 평가셋의 Hit@k·MRR로 확인하는 것입니다. bge-m3 벡터의 양자화 방식을 비교 평가해 bbq를 적용했고, 정확도 손실 없이 메모리를 1/7로 줄였습니다.

    꼬리: 문서 수와 차원으로 벡터 메모리를 어림하면 얼마인가요?

### 임베딩 검색 점수가 이상하게 나옵니다. 무엇을 확인하나요? {#embedding-mismatch}

??? answer "답 보기"
    색인과 질문에 같은 모델과 같은 정규화를 썼는지부터 봅니다. 다르면 점수가 의미 없어집니다. 모델 이름과 버전을 인덱스 메타데이터로 남겨 두면 확인이 쉽습니다.

    그다음 모델이 질문과 문서에 다른 접두어(instruction prefix)를 요구하는지 모델 카드를 확인하고, 청크가 최대 입력 길이를 넘어 조용히 잘리지 않았는지 토큰 기준으로 확인합니다. 인덱스의 `dims`가 모델 출력 차원과 같은지도 봅니다.

### cosine similarity와 dot product는 어떻게 다른가요? {#cosine-vs-dot}

??? answer "답 보기"
    cosine은 두 벡터의 각도만 보고 길이는 무시합니다. dot product는 길이까지 반영합니다. 벡터를 길이 1로 정규화해 두면 두 값의 순위가 같아지고, dot product가 계산이 더 싸서 정규화 + dot product를 많이 씁니다.

    이때 색인 벡터와 질문 벡터 양쪽에 같은 정규화를 해야 합니다.

## 청킹 {#chunking}

### 청킹은 왜 하고, 청크 크기는 어떻게 정하나요? {#chunk-size}

??? answer "답 보기"
    문서를 검색과 답변 생성에 맞는 단위로 나누기 위해서입니다. 너무 크면 관련 없는 내용이 섞여 검색 정확도가 떨어지고 임베딩 입력 한도를 넘습니다. 너무 작으면 맥락이 잘려 답에 필요한 정보가 흩어집니다.

    크기는 임베딩 모델 입력 한도보다 작게 잡고, 글자 수보다 문단·제목·표 행 같은 구조 경계를 우선합니다. 최종 값은 평가셋으로 몇 가지를 비교해 정합니다.

    꼬리: overlap은 왜 두고, 단점은 무엇인가요?

### 표가 많은 문서는 어떻게 청킹했나요? {#table-chunking}

??? answer "답 보기"
    행 단위로 나누고 각 청크에 머리글을 반복해 붙였습니다. 청크 하나만 봐도 숫자가 어느 열의 값인지 알 수 있게 하는 것이 목적입니다. 글자 수 고정 분할은 표 한 행을 두 청크로 쪼개 숫자와 열 이름을 떼어 놓습니다.

    지식기반 검색 RAG 파이프라인에서 이 표 구조 보존 청커를 만들어 HTML 234건을 15,458청크로 나눴고, 크기 초과 청크는 0건이었습니다.

    꼬리: 머리글 반복이 청크를 키우는 문제는요?

### 대형 표를 나눴더니 청크 크기 초과가 생겼습니다. 어떻게 풀었나요? {#oversized-chunks}

??? answer "답 보기"
    원인은 머리글 반복이었습니다. 행이 많고 열 이름이 긴 표에서 매 청크에 머리글을 다시 붙이니 청크가 최대 2,932자까지 커졌습니다.

    긴 머리글은 반복을 중단하고, 모든 행에 공통인 각주는 별도 청크로 분리했습니다. 그 결과 초과 청크가 183개에서 0개가 됐습니다. 이런 문제는 눈으로는 안 보여서, 청크 크기 분포를 숫자로 검사하는 단계를 둬야 찾습니다.

### 표만 떼어 냈더니 수치 답변이 틀렸습니다. 어떤 정보가 함께 가야 하나요? {#chunk-context-label}

??? answer "답 보기"
    표 바로 앞 소제목, 단위 표기, 기준 시점 같은 짧은 문장입니다. 이게 표와 떨어지면 "어느 기간의 수치인지"를 모릅니다. 실제로 소제목이 빠져 당기·전기 수치 답변이 뒤바뀌었고, 표 앞 짧은 소제목을 표 이름표로 붙여 해당 문항을 정답 처리했습니다.

    일반화하면 청크마다 문서 제목, 소제목 경로 같은 contextual metadata를 함께 저장하는 것입니다.

### 요약이나 예상질문을 청크에 붙이는 이유는 무엇인가요? {#chunk-metadata-enrichment}

??? answer "답 보기"
    사용자가 문서에 없는 표현으로 물어도 찾게 하기 위해서입니다. 본문은 딱딱한 문장인데 질문은 바꿔 말한 형태가 많아서, LLM으로 청크의 요약과 예상질문을 만들어 검색 필드로 함께 둡니다.

    지식기반 검색 RAG 파이프라인에서 설명요약·예상질문 메타데이터 필드로 검색을 확장하는 구조를 설계했고, 요약·예상질문 벡터를 추가한 하이브리드 검색으로 바꿔말한 질문 검색이 16/20에서 18/20으로 올랐습니다. 대신 생성 비용이 들고, 생성 오류가 검색에 섞일 위험이 있습니다.

### Parent-child 청킹은 무엇인가요? {#parent-child-chunking}

??? answer "답 보기"
    작은 청크(child)로 검색해 정밀하게 찾고, 답변 생성에는 그 청크가 속한 큰 단위(parent)를 넘기는 방식입니다. 검색 정확도와 답변 맥락을 둘 다 얻으려는 것입니다.

    맥락이 긴 설명 문서에 잘 맞지만, 저장 구조와 조회 로직이 복잡해집니다.

## 하이브리드 검색 {#hybrid-search}

### 하이브리드 검색은 무엇이고 왜 쓰나요? {#hybrid-why}

??? answer "답 보기"
    키워드 검색(BM25)과 벡터 검색(kNN)의 결과를 합쳐 순위를 매기는 것입니다. BM25는 고유명사·숫자·코드에 강하고 표현이 다르면 못 찾습니다. 벡터는 바꿔 말한 질문에 강하고 정확한 용어 일치를 놓칩니다. 실제 질문은 두 유형이 섞여 있어서 둘을 합치면 한쪽 약점이 덜 드러납니다.

    지식기반 검색 RAG 파이프라인에서 검색 평가셋 22문항으로 BM25·벡터·하이브리드의 Hit@5를 자동 비교했고, 요약·예상질문 벡터를 추가한 하이브리드 검색으로 바꿔말한 질문 검색을 16/20에서 18/20으로 올렸습니다.

    꼬리: 검색이 두 번 도는 만큼 지연은 어떻게 관리하나요?

### RRF는 무엇이고, 점수 가중합과 비교하면요? {#rrf-vs-linear}

??? answer "답 보기"
    RRF는 각 검색 결과의 순위만 써서 `1 / (rank_constant + 순위)`를 더하는 방식입니다. BM25 점수와 cosine 유사도는 크기가 전혀 달라서 그대로 더하면 한쪽이 결과를 지배하는데, RRF는 순위만 보니 정규화 없이 합칠 수 있고 기본값으로도 안정적입니다.

    가중합은 점수를 0~1로 정규화한 뒤 가중치를 줘 더하는 방식이라, 점수 차이를 살려 세밀하게 조정할 수 있지만 데이터가 바뀌면 가중치를 다시 맞춰야 합니다. 그래서 RRF로 시작하고, 평가셋에서 차이가 날 때 가중합을 검토합니다.

### 하이브리드 검색에서 필터를 걸었더니 결과가 거의 비었습니다. 왜 그런가요? {#knn-post-filter}

??? answer "답 보기"
    필터를 kNN 바깥(post-filter)에 걸었기 때문일 가능성이 큽니다. kNN이 먼저 k개를 찾은 뒤 필터가 걸러 내면 k개 중 대부분이 빠질 수 있습니다. kNN 쿼리 안의 `filter`로 걸어 후보를 먼저 줄여야 합니다.

    또 `k`와 `num_candidates`가 작으면 RRF에 들어갈 후보 자체가 부족하므로 `rank_window_size`와 함께 맞춥니다.

### 한국어 BM25 품질이 낮습니다. 무엇을 먼저 보나요? {#korean-bm25}

??? answer "답 보기"
    analyzer를 먼저 봅니다. 한국어는 띄어쓰기 단위로 자르면 조사가 붙어 같은 단어가 다른 token이 되므로 형태소 분석기(nori)를 쓰고, 도메인 용어가 잘못 쪼개지면 사용자 사전에 넣습니다.

    `_analyze` API로 문장이 실제로 어떤 token으로 나뉘는지 확인하고, 질문 쪽과 문서 쪽 analyzer가 같은지도 봅니다.

### Reranker는 언제 붙이나요? {#reranker}

??? answer "답 보기"
    1차 검색이 정답을 상위 수십 개 안에는 가져오는데 순서가 아쉬울 때 붙입니다. 상위 후보만 cross-encoder 같은 무거운 모델로 다시 점수를 매겨 순서를 바로잡습니다.

    전체 문서에 쓰기엔 비싸서 후보 수를 제한하고, 붙이기 전후를 MRR 같은 순위 지표로 비교해 지연 증가만큼 효과가 있는지 봅니다.

## RAG 평가 {#rag-evaluation}

### RAG는 어떻게 평가하나요? {#rag-eval-overview}

??? answer "답 보기"
    검색과 생성을 나눠서 평가합니다. 검색은 정답 근거가 상위에 들어왔는지를 Hit@k, Recall@k, MRR로 보고, 생성은 답이 맞는지를 정답률로 봅니다. 나눠 봐야 틀렸을 때 "못 찾은 것"인지 "찾았지만 잘못 읽은 것"인지 구분됩니다.

    지식기반 검색 RAG 파이프라인에서 검색 평가셋 22문항으로 Hit@5 비교를 자동화했고, HTML 문서 검색·답변 평가셋 27문항으로 정답률 26/27을 확인했습니다.

    꼬리: 평가셋은 어떻게 만들었나요?

### Hit@k와 MRR은 어떻게 다른가요? {#hit-vs-mrr}

??? answer "답 보기"
    Hit@k는 상위 k개 안에 정답이 하나라도 있으면 1인 지표라 단순하지만 순위 차이를 못 봅니다. MRR은 첫 정답 순위의 역수(1위 1, 2위 0.5)를 평균해서 정답이 앞으로 올라오는 개선이 드러납니다.

    예를 들어 표 열 이름 오적재 7청크를 고친 뒤 표 질의의 벡터 MRR이 0.85에서 0.92로 올랐는데, Hit@k만 봤다면 이미 상위 k 안에 있던 정답의 순위 개선은 보이지 않았을 것입니다.

### 생성된 답이 맞는지는 어떻게 자동으로 판정하나요? {#answer-judging}

??? answer "답 보기"
    토큰 판정과 LLM 심판을 함께 썼습니다. 토큰 판정은 기대 답의 핵심 숫자·용어가 들어 있는지 보는 방식이라 싸고 결정적이지만 표현이 다르면 오판합니다. LLM 심판은 표현 차이에 강하지만 비용이 들고 판정이 흔들립니다.

    그래서 검색 → 답변 → 이중 판정(토큰·심판 LLM) 자동 평가 파이프라인을 만들어 탐침 질문 96건을 자동 채점했습니다. 이중 판정의 이점은 두 판정이 엇갈리는 문항만 사람이 보면 된다는 것입니다. 심판에게는 답만 주지 않고 근거와 기대 답을 함께 줘야 그럴듯한 오답을 맞다고 하지 않습니다.

    꼬리: 심판 LLM의 판정 자체는 어떻게 믿을 수 있나요?

### 평가셋이 작으면 어떤 문제가 있나요? {#small-eval-set}

??? answer "답 보기"
    1~2문항 차이가 큰 비율 차이로 보입니다. 예를 들어 20문항에서 2문항은 10%p입니다. 그래서 결과를 비율보다 "몇 문항 중 몇 문항"으로 말하고, 어떤 문항이 바뀌었는지 직접 확인합니다.

    또 평가셋에 맞춰 규칙을 계속 고치면 그 평가셋에만 맞는 과적합이 생깁니다. 특정 약점을 찌르는 새 탐침 질문으로 따로 확인합니다.

### 재청킹했더니 평가셋이 쓸모없어졌습니다. 왜 그렇고, 어떻게 막나요? {#eval-set-chunk-id}

??? answer "답 보기"
    정답 근거를 청크 id로만 저장했기 때문입니다. 청킹 규칙을 바꾸면 청크 id가 다 바뀌어 정답 매칭이 깨집니다.

    정답 근거를 문서 id와 근거 문장(또는 핵심 값)으로 저장하고, 평가 때 검색된 청크가 그 근거를 포함하는지로 판정하면 재청킹 후에도 평가셋을 그대로 씁니다.

### 검색 지표는 좋은데 답이 틀립니다. 어디를 보나요? {#retrieval-ok-answer-wrong}

??? answer "답 보기"
    "찾았지만 잘못 읽은" 실패입니다. 검색된 청크를 직접 열어 보고, 숫자 해석에 필요한 맥락(기간, 단위, 열 이름)이 청크 안에 있는지 확인합니다.

    실제로 표 앞 소제목이 빠져 당기·전기 수치 답변이 뒤바뀐 경우가 이것이었고, 검색 지표만 봤다면 놓쳤을 문제입니다. 소제목을 표 이름표로 붙여 해결했습니다. 맥락이 충분한데도 틀리면 프롬프트에 "근거에 없는 값은 답하지 말라"는 지시와 근거 인용을 요구합니다.

## NL2SQL {#nl2sql}

### NL2SQL 에이전트는 어떻게 동작하나요? {#nl2sql-flow}

??? answer "답 보기"
    사용자 질문과 스키마 설명을 LLM에 주고 SQL을 생성하게 한 뒤, 그 SQL을 검증해 실행하고 결과를 요약·시각화합니다.

    개인 프로젝트 Smart Factory Data Agent의 흐름은 사용자 질문 → FastAPI → LLM → SQL 생성 → PostgreSQL → KPI·데이터 분석 → Plotly 시각화 → 결과 제공입니다. 스마트 팩토리·물류 KPI를 자연어로 묻게 했고, 질문은 SELECT 전용 SQL로만 변환했습니다.

    꼬리: 문서 RAG와 NL2SQL은 어떤 질문에 각각 맞나요?

### LLM이 만든 SQL을 안전하게 실행하려면요? {#nl2sql-safety}

??? answer "답 보기"
    코드 검사와 DB 권한, 두 겹으로 막습니다. 실행 전에 SQL 파서로 SELECT 하나인지, 허용한 테이블·view만 참조하는지 확인하고, DB 계정은 읽기 권한만 줍니다. 코드 검사가 뚫려도 계정 권한에서 막힙니다.

    여기에 LIMIT 강제와 statement timeout을 걸어 잘못된 조인으로 수백만 행을 읽는 사고를 막습니다. UPDATE, DELETE, 여러 문장을 세미콜론으로 이은 경우는 실행 전에 거절합니다.

### SQL은 오류 없이 도는데 답이 틀립니다. 어떤 경우인가요? {#nl2sql-semantic-errors}

??? answer "답 보기"
    의미가 틀린 SQL입니다. 대표적으로 지표 계산식 오류(불량률 분모를 잘못 고름), 잘못된 조인으로 행이 중복되어 합계가 부풀어짐, "지난달" 같은 기간 조건 누락이나 임의 해석입니다. 오류가 안 나서 더 위험합니다.

    대책은 지표 정의를 view나 glossary로 고정해 모델이 계산식을 추측하지 않게 하고, 조인 관계를 스키마 설명에 명시하고, 기준 날짜를 프롬프트에 넣는 것입니다. 정답 SQL이 있는 평가셋으로 실행 결과를 비교(execution accuracy)합니다.

### 테이블이 수백 개라면 스키마를 어떻게 프롬프트에 넣나요? {#nl2sql-schema-linking}

??? answer "답 보기"
    전부 넣지 않고 질문과 관련된 테이블만 골라 넣습니다. 테이블·컬럼 설명을 검색 대상으로 색인해 두고 질문으로 후보 테이블을 찾은 뒤, 그 테이블의 컬럼 이름·타입·설명·예시 값을 넣습니다.

    질문의 단어를 실제 컬럼에 연결하는 schema linking이 NL2SQL 실패의 가장 큰 원인이라, 컬럼 이름이 불친절하면 설명을 보강하고 few-shot으로 "질문 → 정답 SQL" 예시를 몇 개 넣습니다.

### 생성된 SQL이 실패하거나 빈 결과가 나오면 어떻게 하나요? {#nl2sql-self-correction}

??? answer "답 보기"
    오류 메시지나 빈 결과를 다시 LLM에 주고 SQL을 고치게 하는 self-correction 루프를 둡니다. 같은 프롬프트로 그대로 재시도하면 같은 오류를 반복하므로, 직전 SQL과 오류 내용을 함께 넣고 최대 횟수를 정합니다.

    빈 결과는 오류가 아니라서 그대로 "데이터 없음"으로 답하기 쉬운데, 조건 오해일 수 있으니 재확인 대상으로 둡니다. 횟수를 넘기면 실패를 사용자에게 그대로 알립니다.

### KPI 같은 지표 계산을 LLM에 맡겨도 되나요? {#nl2sql-kpi-definition}

??? answer "답 보기"
    계산식 자체는 맡기지 않습니다. OEE, 납기 지연처럼 정의가 정해진 지표는 view나 계산 코드로 고정하고, LLM은 어떤 지표를 어떤 조건으로 조회할지만 고르게 합니다. 그래야 사람마다, 호출마다 다른 계산이 나오지 않습니다.

    Smart Factory Data Agent에서는 OEE, 납기 지연, 피킹 생산성, 불량률 KPI를 계산해 Plotly 차트로 보여 주고, KPI 분석 → 근본 원인 분석 → 시각화를 하나의 흐름으로 묶었습니다.

    !!! note "채울 것"
        KPI 계산을 SQL view, Pandas 코드, LLM 생성 SQL 중 어디서 했는지 실제 구현을 확인해 적어 둡니다.

## VLM {#vlm}

### VLM은 무엇이고, RAG 파이프라인에서 어디에 쓰나요? {#vlm-basics}

??? answer "답 보기"
    이미지를 시각 토큰으로 바꿔 텍스트와 함께 언어 모델에 넣는 멀티모달 모델입니다. RAG에서는 파서가 못 읽는 차트·도식·스캔 이미지의 정보를 텍스트 설명으로 꺼내 색인할 때 씁니다.

    다만 텍스트 레이어가 있는 PDF의 글자와 표는 파서가 1순위이고, VLM은 그림 의미처럼 파서로 안 되는 부분에 보조로 씁니다.

### VLM이 그림에 없는 내용을 지어냈습니다. 어떻게 해결했나요? {#vlm-hallucination}

??? answer "답 보기"
    지식기반 검색 RAG 파이프라인에서 그림 설명을 생성할 때 없는 내용을 지어내는 문제가 있었습니다. 작은 이미지를 대상에서 빼고, 로컬 VLM(Qwen2.5-VL-7B)으로 설명을 다시 생성해 그림 28개의 제목·축·글자 추출을 개선했습니다.

    일반적인 대책은 세 가지입니다. 로고·아이콘 같은 작은 이미지는 크기·종류 필터로 먼저 뺍니다. "설명하라" 같은 열린 지시 대신 제목, 축, 범례처럼 필드를 정하고 "보이지 않으면 null"을 명시합니다. VLM이 읽은 숫자는 텍스트 레이어나 OCR과 대조합니다.

    꼬리: 개선됐다는 것은 어떻게 확인했나요?

### 로컬 VLM과 API VLM은 어떻게 고르나요? {#local-vs-api-vlm}

??? answer "답 보기"
    데이터가 외부로 나가도 되는지, 양이 얼마나 되는지로 고릅니다. 외부 전송이 제한되거나 대량 문서를 일괄 처리하면 로컬 모델(GPU 고정비), 소량·고품질이나 영상 분석, 빠른 시작이 중요하면 API(호출당 과금)입니다.

    로컬은 서빙·배치·GPU 메모리를 직접 관리해야 하고, API는 키 관리, rate limit, 재시도가 필요합니다. 성능은 대체로 큰 API 모델이 높습니다.

### 영상 분석은 어떻게 했나요? 실패하면요? {#vlm-video-fallback}

??? answer "답 보기"
    개인 프로젝트 AI 기반 숏폼 영상 생성 시스템에서 Gemini 멀티모달 API로 레퍼런스 영상의 톤·페이싱·훅 패턴·카메라 구도·컷 리듬을 분석해 Style Profile(`style_profile.json`)로 추출했습니다.

    영상 직접 입력은 길이·코덱·용량 제한으로 실패할 수 있어서 단계별 fallback을 뒀습니다. 원본 분석이 실패하면 오디오를 빼고 짧게 잘라 재인코딩한 clean 영상을 분석하고, 그래도 실패하면 대표 프레임 분석으로 넘어갑니다.

### 이미지 토큰 비용은 어떻게 관리하나요? {#vlm-image-tokens}

??? answer "답 보기"
    해상도를 모델 권장 크기로 맞춥니다. 이미지가 클수록 토큰이 늘어 비용과 지연이 커지고, 너무 작으면 글자를 못 읽습니다.

    또 처리 대상을 필터로 줄입니다. 장식용 이미지나 작은 아이콘은 빼고, 의미 있는 차트·도식만 보냅니다. 같은 이미지를 다시 분석하지 않도록 결과를 캐시합니다.

## LLM API {#llm-apis}

### 수천 번 LLM을 호출하는 배치가 중간에 죽었습니다. 어떻게 복구했나요? {#llm-batch-cache}

??? answer "답 보기"
    호출 결과를 해시 키 캐시로 저장해 재실행 시 완료분을 재사용하게 했습니다. 지식기반 검색 RAG 파이프라인에서 수천 회 외부 LLM 호출 배치가 중간 DNS 오류로 중단됐는데, 결과를 입력 해시를 키로 한 jsonl 캐시에 저장하도록 바꿔 재실행 추가 호출 0회로 복구했고 재과금도 없었습니다.

    재시도만 있고 결과 캐시가 없으면 긴 배치가 죽었을 때 처음부터 다시 호출해 비용을 두 번 냅니다. 캐시 키에는 입력뿐 아니라 모델 이름과 프롬프트 버전을 넣어야 프롬프트를 고친 뒤 옛 결과가 재사용되지 않습니다.

    꼬리: 캐시를 jsonl 파일로 둔 이유는요?

### 어떤 오류는 재시도하고, 어떤 오류는 재시도하지 않나요? {#llm-retry-policy}

??? answer "답 보기"
    일시 오류만 재시도합니다. 429(rate limit)는 `retry-after`만큼 기다리거나 지수 백오프, 5xx나 과부하 응답, DNS·연결 끊김 같은 네트워크 오류는 지수 백오프에 jitter를 더해 재시도합니다.

    400, 401, 403, 404처럼 요청이나 인증 문제는 재시도해도 같은 결과라서 바로 실패시키고 원인을 고칩니다. jitter는 여러 작업이 동시에 재시도해 다시 몰리는 것을 흩기 위한 것입니다.

### LLM API 비용을 줄이려면 어떻게 하나요? {#llm-cost}

??? answer "답 보기"
    호출 수, 입력 토큰, 출력 토큰 순으로 봅니다. 같은 입력은 결과 캐시로 다시 부르지 않고, 긴 공통 앞부분(시스템 프롬프트, 긴 문서)은 prompt caching으로 재사용합니다. prompt caching은 앞부분이 한 글자라도 바뀌면 깨지므로 현재 시각이나 요청 id 같은 바뀌는 값은 뒤쪽 메시지에 둡니다.

    작업 난이도에 맞는 작은 모델을 쓰고, 요청 전에 token counting으로 비용을 추정합니다. 출력은 필요한 필드만 구조화 출력으로 받으면 출력 토큰도 줄어듭니다.

### temperature는 어떻게 정하나요? {#llm-temperature}

??? answer "답 보기"
    작업에 따라 다르게 둡니다. 추출·분류처럼 정답이 있는 작업은 낮게(0) 두어 결과를 안정시키고, 아이디어나 카피 생성처럼 다양성이 필요하면 높게 둡니다.

    개인 프로젝트 AI 기반 숏폼 영상 생성 시스템에서는 훅 유형을 랜덤으로 고르고 temperature를 높게 둬서 같은 입력에도 매번 다른 훅이 나오게 했습니다. 반면 데이터 추출 쪽은 temperature 0과 평가셋으로 회귀를 확인하는 편이 맞습니다. 일부 최신 모델은 sampling 파라미터 대신 reasoning effort 같은 다른 조절 값을 씁니다.

### streaming은 왜 쓰나요? {#llm-streaming}

??? answer "답 보기"
    체감 지연을 줄이고 긴 출력의 타임아웃을 피하기 위해서입니다. 전체 응답을 기다리지 않고 토큰이 생성되는 대로 받아 화면에 바로 보여 줄 수 있습니다. 출력이 길면 하나의 HTTP 응답을 오래 기다리다 타임아웃이 나는 것도 피합니다.

    대신 중간에 끊겼을 때의 처리와, 다 받은 뒤에야 할 수 있는 검증(JSON 파싱, stop reason 확인)을 따로 챙겨야 합니다.

### API 키는 어떻게 관리하나요? 외부 API 장애에는 어떻게 대비하나요? {#llm-key-and-outage}

??? answer "답 보기"
    키는 코드에 넣지 않고 `.env`나 비밀 저장소에 두며 저장소에 올리지 않습니다. 제 프로젝트들도 `OPENAI_API_KEY`, `GEMINI_API_KEY`를 `.env`에만 뒀습니다.

    장애 대비는 재시도·캐시에 더해 대체 경로를 두는 것입니다. AI 기반 숏폼 영상 생성 시스템에서는 Veo quota를 초과하면 MoviePy Ken Burns 이미지 영상으로 대체하게 했습니다. 외부 서비스 장애가 곧 내 배치의 장애가 되므로, 실패 시 어떻게 품질을 낮춰 계속 갈지를 미리 정해 둡니다.
